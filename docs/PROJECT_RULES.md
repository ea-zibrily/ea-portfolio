These rules apply to every change, whether it's written by ea, a collaborator or an AI assistant. If a rule blocks you, change the rule here in a PR (with a reason) instead of quietly breaking it.

**Sources of truth, in priority order**

1. **PRD.md**: *what* we build and why
2. **SYSTEM_DESIGN.md**: *how* it's built
3. **PROJECT_RULES.md** (this file): *how we work* day to day
4. The code. If the code disagrees with the docs, either the code is a bug or the docs are stale. Fix whichever is wrong in the same PR.

## 1. Golden rules (the short version)

1. **Content lives in `src/content/` and `public/`, nowhere else.** No hardcoded names, links or project text inside components.
2. **No hex colors or arbitrary color values in components.** Use semantic token classes only (`bg-surface`, `text-text-muted`, `text-primary`).
3. **Every `<style>` block is `scoped`.** Global CSS lives only in `src/styles/`.
4. **Pre-render safe:** never touch `window`, `document` or `localStorage` at module top level or in `setup()` directly. Only use them in `onMounted` or inside a composable that guards for the browser.
5. **Every image has real `alt` text, explicit `width`/`height`, and is WebP** (generated by `npm run images`).
6. **Check both themes** (light and dark) and **check mobile (360 px)** before opening a PR.
7. **Slugs and section ids never change** once published. They're URLs that people bookmark and share.
8. **No new dependency without a reason** written in the PR description.
9. **Never commit** `node_modules/`, `dist/`, `.env*`, OS junk or editor caches.
10. **`main` is production.** Nothing reaches it without going through `development` and a green Netlify deploy preview.

| Add reusable reactive logic | `src/composables/use<Name>.js` |

### 2.4 Placement rules

- **`content/` holds data only.** Plain objects and arrays, no functions, no imports from Vue. Logic over content goes in `lib/`.
- **`lib/` is pure.** No Vue, no DOM, so it's trivially unit-testable.
- **`ui/` components know nothing about this portfolio.** They take props and slots, never import from `content/`.
- **`sections/` and `project/` components may import from `content/`** and `lib/`.
- **`views/` compose sections.** They hold no markup beyond layout wrappers.
- **No barrel files** (`index.js` re-exporting components). Import the file directly; it's clearer and better for tree-shaking.
- Use the **`@/` alias** for anything outside the current folder (`@/lib/format`), and relative paths only for siblings.

## 4. Vue & JavaScript rules

### 4.1 Component structure

```vue
<script setup>
// 1. imports  2. props/emits  3. composables  4. state  5. computed  6. functions  7. lifecycle
import { computed } from 'vue'
import { formatPeriod } from '@/lib/format'

const props = defineProps({
  item: { type: Object, required: true },
})

const period = computed(() => formatPeriod(props.item.start, props.item.end))
</script>

<template>
  <!-- markup -->
</template>

<style scoped>
/* only when Tailwind can't express it */
</style>
```

- **`<script setup>` + Composition API** in all new or touched code. Migrate Options API files when you touch them; don't mix both in one file.
- Block order: `script` → `template` → `style`.
- **Props:** always declare `type`, plus `required` or `default`. Never mutate props.
- **Events:** declare with `defineEmits`. Name them in kebab-case in templates (`@item-select`).
- **`v-for` always has a stable `:key`** (an id or slug, never the index).
- **Never `v-if` and `v-for` on the same element.** Filter in a `computed` instead.
- **Prefer `computed` over methods** for derived values.
- **No `v-html`.** All content is plain text or arrays of strings. (The old blog's `v-html` was an XSS risk.)
- **No direct DOM manipulation** (`innerHTML`, `querySelector`) in components. Use template refs or a composable.
- **Keep components under ~200 lines.** If a template needs scrolling, split it.

### 4.2 Pre-render (SSG) safety

```js
// ❌ breaks the build: runs on the server
const saved = localStorage.getItem('theme')

// ✅ runs only in the browser
onMounted(() => {
  const saved = localStorage.getItem('theme')
})
```

- Browser APIs (`window`, `document`, `localStorage`, `matchMedia`, `IntersectionObserver`) only inside `onMounted`, event handlers, or composables that do the same.
- Every observer, listener or timer you create is cleaned up in `onBeforeUnmount`.
- Wrap `localStorage` in `try/catch`. It throws in some private-browsing modes.

### 4.3 General JS

- ES modules, `const` by default, `let` only when reassigned, never `var`.
- Use `null` for "no value", never the string `'null'`.
- Dates in content are ISO (`'2025-09'`). Format them only in `lib/format.js`.
- No `console.log` in committed code (ESLint warns).
- Comments explain *why*, not *what*.

## 5. Styling rules

- **Tailwind first.** Write a scoped `<style>` only for things Tailwind can't do cleanly, like complex keyframes or `::after` decorations.
- **Semantic tokens only:** `bg-bg`, `bg-surface`, `bg-surface-hover`, `border-border`, `text-text`, `text-text-muted`, `text-primary`, `bg-primary text-primary-fg`, `text-accent`, `bg-tag`.
  - ❌ `bg-[#1e1e1f]`, `text-amber-200`, `style="color: …"`
  - ✅ `bg-surface`, `text-primary`
- New color → add the token to **both** `:root` and `.dark` in `tokens.css`, check contrast (≥ 4.5:1 for text), and record it in the contrast table there.
- `dark:` variants are only for exceptions (e.g. dimming an image in dark mode). If you're writing many `dark:` classes, you're missing a token.
- **Spacing and sizes:** use the Tailwind scale. Arbitrary values (`mt-[37px]`) need a comment saying why.
- **Animations:** keyframes live in `src/styles/animations.css` with unique names. Every animation must be disabled under `prefers-reduced-motion: reduce`.
- **Class order** is enforced by `prettier-plugin-tailwindcss`. Don't sort by hand.
- **Mobile first:** base classes target mobile, then add `md:`, `lg:`.

## 6. Content rules

- Follow the schemas in PRD F2 (experience) and F5 (projects). `tests/content.spec.js` enforces them.
- **Slugs and section ids are permanent.** If a project is renamed, keep the old slug.
- Optional fields are `null` or omitted, never empty strings or `'null'`.
- **Writing:** English, sentence case for headings, active voice, and a concrete impact where possible ("cut load time by 40%" beats "improved performance"). Run a spell check before committing.
- **Images:**
  - Put originals in `assets-src/` and run `npm run images`. Never put un-optimized files in `public/img/`.
  - Each output should be ≤ 300 KB (the script warns).
  - `alt` describes what's shown ("Gameplay of ELKER 2043: Ele sneaking past a guard"), not "image" or "HTML". Purely decorative images use `alt=""`.
- **External links** use `https://`, and open in a new tab with `target="_blank" rel="noopener noreferrer"`.
- **The CV PDF** keeps the same filename, stays ≤ 1 MB and must be text-selectable.

## 7. Accessibility & performance (must pass before merge)

**Accessibility**
- One `<h1>` per page. Headings are never skipped (`h2` → `h3`, never `h2` → `h4`).
- Everything clickable is a `<button>` or `<a>`, never a `<div @click>`.
- Icon-only buttons have an `aria-label`.
- A visible focus ring on everything (`focus-visible:`). Never `outline: none` without a replacement.
- Text contrast ≥ 4.5:1 in **both** themes.

**Performance**
- Below-the-fold images: `loading="lazy" decoding="async"`. The hero image gets `fetchpriority="high"`.
- Routes other than home are lazy-loaded (`() => import(...)`).
- No hotlinked third-party images, fonts or scripts. Everything is self-hosted.
- Budgets (SYSTEM_DESIGN §11): Lighthouse mobile ≥ 90 performance and ≥ 95 accessibility, home JS < 120 KB gzip, home images < 3 MB.

## 8. Git workflow

### 8.1 Branches

| Branch | Purpose | Deploys to |
|---|---|---|
| `main` | Production. Protected: no direct pushes | Netlify production |
| `development` | Integration. Merge target for all work | Netlify branch deploy |
| `feat/<short-name>` | New feature or phase | Deploy preview via PR |
| `fix/<short-name>` | Bug fix | Deploy preview via PR |
| `chore/<short-name>` | Tooling, deps, cleanup | Deploy preview via PR |
| `content/<short-name>` | Content-only updates (new project, CV) | Deploy preview via PR |

Flow: `feat/*` → PR → `development` → (release) PR → `main`.

### 8.2 Commits ([Conventional Commits](https://www.conventionalcommits.org/))

```
<type>(<optional scope>): <imperative summary, lowercase, ≤ 72 chars>
```

| Type | Use for |
|---|---|
| `feat` | New user-visible feature |
| `fix` | Bug fix |
| `content` | Text, data, CV or image changes only |
| `style` | Visual/CSS changes with no behavior change |
| `refactor` | Code change with no behavior change |
| `perf` | Performance improvement |
| `docs` | Docs only |
| `test` | Tests only |
| `chore` | Tooling, deps, config, cleanup |

Examples: `feat(nav): add scroll-spy highlight` · `content(projects): add ghost pinball write-up` · `fix(theme): prevent flash on reload`

- One logical change per commit. Don't mix a refactor with a feature.
- Never commit generated files except `public/img/` (the optimized output, which is deployed).

### 8.3 Pull requests

- Every PR into `development` or `main` uses the PR template and links the PRD requirement ids it covers (e.g. `Implements F1.2, F1.4`).
- **Squash merge** into `development`. Use a **merge commit** for `development` → `main` releases.
- CI (lint + test + build) must be green, and the **Netlify deploy preview** must be checked by hand.

## 9. Dependencies

- Add a dependency only if writing it yourself would take more than ~50 lines or is security-sensitive. Explain why in the PR.
- Prefer small, maintained, MIT-licensed packages without peer-dependency sprawl.
- Commit `package-lock.json`. CI and Netlify use `npm ci`.
- Node version is pinned in `.nvmrc` and `netlify.toml` (Node 22). Don't upgrade one without the other.
- Major version upgrades get their own `chore/` PR, never bundled with features.

## 11. Rules for AI assistants

These also live in [`/CLAUDE.md`](../CLAUDE.md), so Claude Code loads them automatically.

- Read the PRD, SYSTEM_DESIGN and this file before changing structure. Follow them over personal preference.
- Work on a `feat/` / `fix/` / `chore/` / `content/` branch, never directly on `main` or `development`.
- Commit or push only when ea asks.
- Don't invent content: experience, project write-ups, dates or metrics come from ea. Use clearly marked `TODO(ea):` placeholders instead.
- Keep changes scoped to the requested phase or requirement. Note unrelated issues, but don't fix them silently.
- When a rule here and a request conflict, point out the conflict before acting.
