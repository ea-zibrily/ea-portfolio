These rules apply to every change, whether it's written by ea, a collaborator or an AI assistant. If a rule blocks you, change the rule here in a PR (with a reason) instead of quietly breaking it.

**Sources of truth, in priority order**

1. **PRD.md**: *what* we build and why
2. **SYSTEM_DESIGN.md**: *how* it's built (as built, plus known issues in §13)
3. **PROJECT_RULES.md** (this file): *how we work* day to day
4. The code. If the code disagrees with the docs, fix whichever is wrong in the same PR.

> Rules marked **(target)** aren't fully met by the current code yet. The related known issue (K-xx in SYSTEM_DESIGN §13) tracks the gap. New code must follow the rule anyway.

## 1. Golden rules

1. **Content lives in `src/content/` and `public/`, nowhere else.** No hardcoded names, links or project text inside components.
2. **Colors only through semantic tokens** (`bg-surface`, `text-text-muted`, `text-primary` …). No hex values and no raw palette classes (`zinc-*`, `red-*`) in components **(target, K-07)**.
3. **Every `<style>` block is `scoped`.** Global CSS lives only in `src/styles/`.
4. **Pre-render safe:** never touch `window`, `document` or `localStorage` at module top level or directly in `setup()`. Use `onMounted`, handlers or a guarded composable. **Clean up every timer, observer and listener** in `onBeforeUnmount`.
5. **Every image is WebP, has real `alt` text, and has explicit `width`/`height`.**
6. **Check both themes and 360 px width** before opening a PR.
7. **Slugs and section ids never change** once published.
8. **No new dependency without a reason** written in the PR description.
9. **Never commit** `node_modules/`, `dist/`, `.env*` or OS/editor junk **(target, K-13: `dist/` is still tracked)**.
10. **Production only changes through a reviewed PR** with a green Netlify deploy preview.

### 2.3 Placement rules

- **`content/` holds data only.** Plain objects and arrays, no functions, no Vue imports.
- **`lib/` is pure.** No Vue, no DOM. Logic shared between a component and a test belongs here (e.g. project category matching).
- **`ui/` components know nothing about this portfolio.** They take props and slots and never import from `content/`.
- **`sections/` and `project/` components may import from `content/` and `lib/`.**
- **`views/` compose sections and own page-level concerns** (meta tags, JSON-LD, scroll-spy setup).
- **No barrel files.** Import components directly.
- **Use the `@/` alias** for anything outside the current folder.
- **Delete unused components and assets** in the same PR that stops using them.

## 4. Vue & JavaScript rules

### 4.1 Component structure

```vue
<script setup>
// 1. imports  2. props/emits  3. composables  4. state  5. computed  6. functions  7. lifecycle
</script>

<template>
  <!-- markup -->
</template>

<style scoped>
/* only when Tailwind can't express it */
</style>
```

- **`<script setup>` + Composition API** everywhere.
- Block order: `script` → `template` → `style`.
- **Props:** always declare `type`, plus `required` or `default`. Never mutate props.
- **`v-for` always has a stable `:key`** (an id, slug or the value itself for string lists). Use the index only for static lists of strings that never reorder.
- **Never `v-if` and `v-for` on the same element.**
- **Prefer `computed` over methods** for derived values.
- **No `v-html`.**
- **No interactive element inside another** (no `<a>` or `<button>` inside an `<a>`) **(target, K-02)**.
- **Keep components under ~200 lines.** Repeated markup blocks (e.g. the five link buttons in `ProjectDetailView`) should become a `v-for` over data or a small component.

### 4.2 Pre-render (SSG) safety

```js
// ❌ breaks the build: runs during pre-rendering
const saved = localStorage.getItem('theme')

// ✅ runs only in the browser
onMounted(() => {
  const saved = localStorage.getItem('theme')
})
```

- Browser APIs only inside `onMounted`, event handlers, or composables that guard with `typeof window`.
- Every `setTimeout`/`setInterval`, observer and listener is cleared in `onBeforeUnmount` **(target, K-12)**.
- Wrap `localStorage` in `try/catch`.

### 4.3 General JS

- ES modules, `const` by default, never `var`.
- `null` for "no value", never `'null'` or `''`.
- Dates in content are ISO (`'2025-09'`), formatted only in `lib/format.js`.
- No `console.log` in `src/` (scripts may log).
- Comments explain *why*, not *what*.

## 5. Styling rules

- **Tailwind first.** Use a scoped `<style>` only for keyframes, pseudo-elements or things Tailwind can't express.
- **Semantic token classes:** `bg-bg`, `bg-surface`, `bg-surface-hover`, `border-border`, `text-text`, `text-text-muted`, `text-primary`, `bg-primary text-primary-fg`, `text-accent`, `bg-tag`. Opacity modifiers are fine (`bg-primary/10`, `border-border/50`).
- **Not allowed in components (target, K-07):** hex values, `bg-[#…]`, raw palette classes (`zinc-*`, `red-*`, `white`, `black`), inline `style="color: …"`. If you need a new meaning (danger, overlay), add a token.
- **New token** → add it to both `:root` and `.dark` in `tokens.css`, map it in `@theme inline` in `main.css`, and add it to `tests/theme.spec.js`.
- **Contrast:** text must reach ≥ 4.5:1 on **every background it's placed on** (not just `--bg`), in both themes. Muted text on `bg-tag` or `bg-surface-hover` is the usual weak spot (K-06).
- **Layout values:** use the Tailwind scale. Arbitrary values are fine only for token-based math (`scroll-mt-[var(--nav-h)]`, `min-h-[calc(100vh-var(--nav-h))]`).
- **Animations** respect `prefers-reduced-motion` (disable them or reduce them to an opacity change).
- **Mobile first:** base classes target mobile, then add `sm:`, `md:`, `lg:`.

## 6. Content rules

- Follow the schemas in PRD F2 (experience) and F5 (projects). Tests in `tests/` enforce them. Extend the tests when you add a field.
- **Slugs and ids are permanent.**
- Optional fields are `null` or `[]`. Never use `'null'` or `''`.
- **Writing:** English, sentence case for headings, active voice, concrete impact where possible. Spell-check before committing.
- **Images:**
  1. Put the original PNG/JPG in `assets-src/` using the naming in §3.
  2. Run `npm run images` to produce `public/img/<name>.webp` (portfolio ≤ 1200 px, certificate ≤ 800 px, profile ≤ 500 px).
  3. Reference the `.webp` path in content. **Never commit PNG/JPG under `public/img/`** **(target, K-01: the script still reads from `public/img/` until it's fixed)**.
  4. Each WebP should be ≤ 300 KB.
- **Project media:** `cover` is required. `gallery` holds extra screenshots (the detail page shows cover + 2). `video` is a YouTube URL.
- **External links** use `https://` and open with `target="_blank" rel="noopener noreferrer"`.
- **Placeholders:** use `TODO(ea): …` strings for missing personal data, and never render them. A component that would show a `TODO(ea)` value must hide it.

## 7. Accessibility & performance (must pass before merge)

**Accessibility**
- One `<h1>` per page. Never skip heading levels.
- Clickable things are `<button>` or `<a>`, never a `<div @click>`. No nested interactive elements.
- Icon-only buttons and links have `aria-label`.
- Visible focus ring (`focus-visible:`). Never `outline: none` without a replacement.
- Decorative visuals (loader, glows, icons next to text) use `aria-hidden="true"`, not `role="status"` (K-17).

**Performance**
- Below-the-fold images: `loading="lazy" decoding="async"`. Only the hero image gets `fetchpriority="high"`.
- Non-home routes are lazy-loaded.
- Heavy embeds (YouTube) load on user action, not on page load **(target, K-09)**.
- Third-party requests are allowed only for Google Fonts and YouTube. Icons get self-hosted **(target, K-14)**.
- Budgets: Lighthouse mobile performance ≥ 90 and accessibility ≥ 95. Home images < 3 MB.

## 8. Git workflow

### 8.1 Branches

| Branch | Purpose |
|---|---|
| `main` | Default branch on GitHub |
| `development` | Integration. Target of all work branches |
| `staging` | Pre-release check |
| `production-v<major>.<minor>` | Release snapshots (`production-v1.0`, `production-v1.1`) |
| `feat/…` · `fix/…` · `chore/…` · `content/…` · `docs/…` | Short-lived work branches off `development` |

Flow: work branch → PR → `development` → `staging` → `production-v*` / `main`.

> ⏳ **To confirm:** which branch Netlify publishes to production. Until then, treat both `main` and the latest `production-v*` as protected (no direct commits).

### 8.2 Commits ([Conventional Commits](https://www.conventionalcommits.org/))

```
<type>(<scope>): <imperative summary, lowercase, ≤ 72 chars>
```

| Type | Use for |
|---|---|
| `feat` | New user-visible feature |
| `fix` | Bug fix |
| `content` | Text, data or image changes only |
| `style` | Visual/CSS change with no behavior change |
| `refactor` | Code change with no behavior change |
| `perf` | Performance |
| `docs` | Docs only |
| `test` | Tests only |
| `chore` | Tooling, deps, config, cleanup |

Common scopes: `layout`, `content`, `theme`, `nav`, `project`, `seo`, `build`, `deps`.

Examples: `content(projects): add humans portfolio` · `fix(layout): nested links in portfolio card` · `chore(build): untrack dist`

> Recent history used `feat(content): …` for content changes. Prefer `content(<area>): …` from now on, so content updates are easy to spot in the log.

- One logical change per commit.
- Never commit build output (`dist/`) or generated sitemaps from local builds.

### 8.3 Pull requests

- PRs into `development` reference the PRD requirement or known-issue ids they cover (`Implements F6.5`, `Fixes K-02`).
- **Squash merge** into `development`. Use **merge commits** for release merges.
- `npm test` and `npm run build` must pass, and the Netlify deploy preview must be checked by hand.

## 9. Dependencies & environment

- Add a dependency only if writing it yourself would take more than ~50 lines or is security-sensitive. Explain why in the PR.
- Commit `package-lock.json`. Netlify uses `npm ci`.
- **Node 22** is pinned in `.nvmrc` and `netlify.toml`. Use it locally too (`nvm use`); newer Node versions can hide build differences.
- Remove dependencies as soon as they're unused (e.g. `@fontsource/poppins`, K-15).
- Major upgrades (Vite, Tailwind, vite-ssg) get their own `chore(deps)` PR.

## 11. Rules for AI assistants

These also live in [`/CLAUDE.md`](../CLAUDE.md), so Claude Code loads them automatically.

- Read the PRD, SYSTEM_DESIGN (including §13 known issues) and this file before structural changes.
- Work on a `feat/` / `fix/` / `chore/` / `content/` / `docs/` branch, never directly on `main`, `development`, `staging` or `production-v*`.
- Commit or push only when ea asks.
- Don't invent content: experience, project write-ups, dates or metrics come from ea. Use `TODO(ea):` placeholders.
- Keep changes scoped to the request. Note unrelated issues (or add them to SYSTEM_DESIGN §13) instead of fixing them silently.
- When a rule and a request conflict, point out the conflict before acting.
- When the code changes in a way that makes these docs wrong, update the docs in the same change.
